## 1. 凭证录入卡片改为组件机制（未开始）

**结论**：`secret_request` 的录入卡片应改为平台内置的 `kind=component`（DSL）组件，而不是现在写死在 `ChatPanel` 里的 TSX。方向已确认，本轮不实施。

> 与「会话内插件配置」（`docs/插件体系设计.md` §7.5）合流：两者都在会话里渲染可写卡片，必须共用同一条组件通道，不各留一个 TSX 特例。多机器人（§16）的配置入口也落在同一张卡片上。

**现状**

- 工具是 Go 内置：`internal/tool/secrets.go`（`secret_request`）+ `internal/tool/builtin.go:38` 注册，`Registry.Load` 只按系统空间的停用记录过滤（`disabledBuiltinTools`），其余装载逻辑与插件体系无关。
- 卡片是硬编码前端：`web/src/components/SecretRequestCard.tsx`，由 `web/src/components/ChatPanel.tsx:136-180` 按工具名分支渲染——平台为单个工具开了专属渲染通道，这是“不统一”的根因。
- 市场里只有一条元数据影子插件 `tool_secret_request`（`internal/plugin/seed.go:70-88`），无代码、不影响能力。

**为什么改**：卡片变成可版本化、可复制、可按业务扩展的资产（如 MCP 场景需要“账号 + 密码 + 域名”多字段），其他人可安装、可借鉴，而不是读源码抄 TSX。

**必须同时补的三条边界**（不补则组件化后安全性低于现状）

1. 新增**不经工具链路**的动作 `secret.save`：浏览器直连 `PUT /admin/secrets/{scope}/{name}`。现有 `invoke`（走 `/data` → 工具调用）与 `message`（填进输入框）都会让明文过宿主链路或进入上下文，违反 `docs/技术方案.md:474`。
2. 新增独立节点 `SecretInput`：值不写进 `state`。现有 `Input` 的值进 `state`，而 `state` 参与 `data.*` 参数模板与 `message` 插值（`web/src/components/UiBlock.tsx:118-122`、`145-147`），密码不能复用。
3. `secret.save` 必须**清单白名单化**：在 `capabilities` 声明可请求录入的 `scope/name`（复用 `secret.use` 的 `Name` 语义，`internal/plugin/manifest.go:117-126`），安装时由 `Manifest.Permissions()` 展示，运行期越界拒绝；并禁止 `kind=component` 声明 `secret.use`（组件无执行器，同时声明等于诱导录入后自取）。

**落地步骤（先文档后代码）**

1. `docs/技术方案.md` §5.5.2 改为“组件渲染 + 浏览器直连写入”；§5.8.2/5.8.5 补 `SecretInput` 节点、`secret.save` 动作、`secret.request` 能力白名单、component 禁 `secret.use`。
2. `internal/space/plugin_dev_docs.go` 的组件子手册同步 DSL 全表。
3. 代码顺序：`internal/plugin/dsl.go` → `web/src/components/UiView.tsx` / `UiBlock.tsx` → `internal/tool/secrets.go`（回执改为通用 `component` 字段）→ `ChatPanel` 通用化并删除特例 → `internal/plugin/seed.go` 发内置 `secret_form` 组件。
4. 安全规则（能力白名单、component 禁 `secret.use`）与功能同一次提交，不留中间态。

**验收**

- 会话里 `secret_request` 返回 `state=missing` 时渲染的是已安装组件，明文只走 `PUT /admin/secrets`，`run_step` 与消息体里无明文。
- 组件声明未授权的 `scope/name` 时，发布/试运行即被拒绝。
- `ChatPanel` 不再包含任何按工具名的渲染分支。

## 7. 多机器人（未开始）

**结论**：多机器人不是平台概念。渠道插件（钉钉 / 企微）由平台用户开发，接几台机器人、每台用哪套凭证、投给哪个智能体，都由插件作者在自己的配置里声明。平台只提供两样能力：**`records` 配置类型**（使用者可增删的对象数组，`docs/插件体系设计.md` §4.7）与**入站按智能体分流会话**（§16）。

平台不做：默认机器人、智能体级机器人绑定（`plugin_agent_config`）、按机器人拆进程 / 令牌 / 出网代理。这套方案已废弃——平台不知道渠道插件内部有几台机器人，也定不出一份有意义的默认值。

**现状**

- 配置类型只有标量 + `list`（逗号分隔字符串），装不下「每项有 AppKey / RobotCode / 密钥 / 智能体」的结构。
- `config.get` 返回 `map[string]string`，`ConfigView.Values` 与 `UpdateConfig` 也都是字符串表。
- 入站 `IMInboxItem` 没有 agent 字段，会话唯一键是 `(channel, created_by)`。
- 凭证 scope 全局 `plugin`、`secret.use` 是静态白名单，动态数量的凭证名过不了校验。

**落地步骤**

1. **P7.1 `records` 与 `agent_ref`**：`ConfigItem` 增加 `item`（`title_key` + `fields`）与 `max_items`，`Default` 从 `string` 改 `json.RawMessage`；新增 `agent_ref` 类型（存本空间智能体 slug，保存时校验可用性，失效不阻断其他字段保存）；`validateConfigValue` 递归校验、未知子键拒绝、整体 32KB 上限；`UpdateConfig` 对 `records` 解析 JSON 字符串后按数组落库；`config.get` 返回值放宽，`records` 直接返回数组；`invokeInput` 加 `AgentID` 并新增 `invoke.context` 宿主方法（预热期报错，不兜底）。验收：声明一条 `bots` 能配 3 台，`wa.config().bots.length === 3`；`wa.context().agentId` 在并发调用下各自正确；`agent_ref` 填不存在的 slug 直接报错。
2. **P7.2 入站分流**：`IMInboxItem` 加 `agent`（可选），校验该智能体在本空间可用，不传落 `base`；会话唯一键改 `(channel, coalesce(agent_id,'base'), created_by)` 并回填历史；去重键加 agent。验收：机器人 1 的消息进 A 的会话、机器人 2 进 B；同一 `ref` 重投不跑第二轮。
3. **P7.3 配置表单并入 DSL**：`configToDsl(ConfigView)` 产出 `{dsl:'wa-ui/1', view, state}`，`PluginConfigDialog` 与 `plugin_setup` 卡片都改走 `UiView`；DSL 配置档新增 `submit` 动作与 `SecretInput` 节点（`rt.secrets` 独立表），作者档校验白名单不含这两个；`RecordList` / `Switch` / `Textarea` 进公共档。验收：`PluginConfigDialog` 里不再有按 `field.type` 的分支；作者 `ui.json` 写 `submit` 解析失败；密钥在 state、`invoke` 参数、错误回显里都找不到。

**已定（2026-11）**

- 机器人数量：平台不设上限；一个插件一个进程，多机器人是进程内的多条连接。
- 凭证：授权边界是实例 scope `plugin:<空间>|<slug>`，名字可以动态；`secret.use` 只用于安装页「缺哪些凭证」的提示。已装插件由空间 `manage` 录，未发布草稿由开发者（空间 `write`）录，平台级 scope 仍只归系统管理员。
- 渠道插件走市场、按空间安装，不做成 `origin=system` 的单点内置件（那份配置全局唯一，所有空间会共用一个机器人列表）。
