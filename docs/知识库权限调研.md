# 企业知识库权限与 LLM Wiki 规范调研

本文是调研记录，不是实现标准。结论落地前需要并入《技术方案》对应章节（§5.5 资源与能力、§5.7.4 记忆与知识库），**先改方案再改代码**。

调研问题有两个：

1. 企业的「知识」是怎么分权限管理的？
2. LLM wiki 这个形态有没有成文规范，规范里有没有权限？

---

## 1. 结论摘要

1. **权限只有一个作用点问题**：组织级 → 容器级（空间 / 知识库 / workspace）→ 节点级（页面 / 目录，继承 + 例外）→ 文档级（ACL 挂在索引上）。越往下越细，工程代价陡增，没有任何一家同时把四层都做满。
2. **主流产品收敛在「容器 + 节点继承」两层**：飞书知识库、Confluence 都是「空间权限 + 页面限制」，页面默认继承父级，**子级只能收紧、不能放宽，也不能超出父级上限**。
3. **文档级 ACL 是检索侧的工程问题，不是权限设计问题**。把层级权限投影到扁平向量空间，会同时产生查询延迟、权限漂移、重建索引写放大三类失败模式；微软自己的做法也是「查询时只比对已同步到索引的元数据」，因此**撤销天然存在窗口**。
4. **LLM wiki 没有正式规范**。事实标准是 Karpathy 2026-04-04 的 gist（`raw/` + `wiki/` + schema 三层），最接近成文的是 WikiHub 的《The LLM Wiki Format》，但它**明确定义了内容结构、没有定义任何权限模型**——无角色、无 ACL、无审批、无并发冲突解决。
5. 对本平台的含义：我们的 wiki 是「容器级权限」，方向正确但停在最粗的一层；缺失的是节点级能力、`list`/`search` 的泄露面收敛、以及内容级审计。这三项不需要引入向量库，改动量可控。

## 2. 企业知识库的四种权限作用点

| 作用点 | 代表实现 | 权限语义 | 优点 | 代价 |
|---|---|---|---|---|
| **组织级 / 全局级** | Confluence global permissions、飞书 Admin 控制台 | 谁能建库、能否对外分享、文件操作总开关 | 一处收紧全局生效 | 粒度太粗，只能当兜底 |
| **容器级**（空间 / 知识库 / workspace） | 飞书知识空间、Confluence space、容器化 RAG 方案 | 成员角色（管理员 / 编辑 / 阅读），容器内文档共享同一权限边界 | 零查询过滤、零漂移、零重建索引 | 放弃文件级粒度，「谁能进容器」成为治理核心 |
| **节点级**（页面 / 目录，继承 + 例外） | 飞书子页面、Confluence page restrictions | 默认向下继承；子级只能收紧 | 细粒度且可解释 | 继承链判定复杂，权限复核成本高 |
| **文档 / chunk 级 ACL** | Azure AI Search、Glean | 每文档带 ACL / RBAC scope / 敏感度标签，查询时裁剪 | 与源系统权限一一对应 | 延迟、漂移、写放大 |

### 2.1 飞书知识库：三层 + 继承只能收紧

- 三层：组织级（能否新建知识空间、对外分享）→ 知识空间（管理员 / 成员，可编辑 / 可阅读）→ 页面（协作者 + 链接分享范围 + 权限设置）。
- 子页面默认继承父级的协作者、链接分享范围、权限设置；解除继承后，**权限设置仍只能在父级允许的范围内修改**，要放宽必须找父级所有者。
- 空间管理员拥有空间内全部文档权限，可批量管控授权范围。
- 权限主体支持组织架构：部门、用户组、成员维度直接授权。

### 2.2 Confluence：三级，但继承有历史缺陷

- 三级：global permissions → space permissions → page restrictions。
- 页面限制只有 view / edit 两种动作。
- 已知问题：子页面**继承 view 但不继承 edit**，官方长期不修（认为这是产品定位使然）。这正好说明「继承语义一旦定错，后面很难纠正」。

### 2.3 Azure AI Search：四种文档级方法

| 方法 | 机制 | 状态 |
|---|---|---|
| Security filters | 应用把用户 / 组标识作为字符串传入 query filter，排除不匹配文档 | GA，API 无关 |
| POSIX-like ACL / RBAC scopes | 用查询 token 中的 Entra 主体与文档权限元数据比对 | 预览 |
| Purview 敏感度标签 | 索引器抽取标签，查询时按标签 + 策略判定 | 预览 |
| SharePoint ACL | 索引器抽取 SharePoint 原生权限（含站点组） | 预览 |

官方文档里的几条硬事实：

- **查询时只比对「已同步到索引」的权限元数据，不实时回源**。源端收紧后要等下次 indexer 运行才生效，存在权限残留窗口；继承自父级的变更还需要显式刷新。
- 建议**以组授权代替个人授权**，否则个人 ACL 数量会失控。
- ACL 字段在分块场景要投影到每个 chunk，否则 chunk 级引用不会被过滤。
- 客户端应用自身的索引读权限（Search Index Data Reader）与文档级权限是**两道独立检查**。

### 2.4 Glean 与容器化方案

- Glean 的卖点是 100+ connector 的权限感知同步 + 查询时执行，属于「索引期绑定 + 查询时裁剪」路线。
- 容器化方案（fast.io 等，厂商文章需打折）主张把安全边界从 chunk 上移到 workspace：权限即成员资格，检索只在成员所属容器内作答，从而消除查询时 ACL 过滤、权限漂移、payload 重写三个问题。代价是容器内无文件级权限。

## 3. 检索侧的三条工程路线

| 路线 | 做法 | 成立条件 | 失效方式 |
|---|---|---|---|
| **索引期打 ACL + 查询时裁剪** | ACL 挂 chunk metadata，查询前 / 中过滤 | 数据量小、组结构扁平稳定 | 组扩展拖慢查询；HNSW 图被过滤打碎；权限变更触发批量 payload 重写 |
| **容器隔离** | 权限即容器成员资格，向量库不承担权限语义 | 能事先界定访问边界 | 失去文件级粒度；边界模糊的内容需要治理决策 |
| **运行时 OBO 回源校验** | 检索到候选后拿用户 token 回调源系统校验 | 候选少、QPS 低、源 API 配额充足 | 每候选一次网络往返；限流 429 打断流程；源抖动级联为不可用 |

两种过滤时机的问题也被反复提到：

- **后过滤**（先全局召回再丢弃）是安全反模式：高相关内容往往就在机密文件里，丢弃后 prompt 为空；被丢弃的 ID 若出现在日志或排序管道里，就是侧信道。
- **预过滤**（打分前约束候选集）是性能陷阱：把图遍历限制在动态稀疏子集上。

结论：**问题不在过滤策略，而在把层级权限投影到扁平空间这一架构错配**。

## 4. LLM wiki 的规范现状

### 4.1 已成事实标准的部分（Karpathy 模式）

三层结构，所有权清晰：

| 层 | 目录 / 文件 | 所有者 |
|---|---|---|
| 原始资料（不可变） | `raw/`（articles / papers / assets） | 人，LLM 只读 |
| 编译产物 | `wiki/`（entities / concepts / sources + `index.md` + `log.md`） | LLM 全权维护 |
| Schema | `CLAUDE.md` 或 `AGENTS.md` | 人 + LLM 共同演进 |

三个必需文件：

- `index.md`：内容目录，每页一行链接 + 一句摘要，答题前先读它找路。
- `log.md`：**只追加**的时间序日志，记录每次 ingest / query / lint。
- Schema 文件：目录结构、命名规则、frontmatter 字段、交叉引用规则、三种操作的步骤。被实践者称为「整个仓库最重要的文件」。

页面 frontmatter：

| 字段 | 含义 |
|---|---|
| `title` | 页标题 |
| `tags` | 标签数组 |
| `date` | `YYYY-MM-DD` |
| `source_count` | 来源数量 |
| `status` | `active` / `superseded` / `archived` |
| `confidence` | `high` / `medium` / `speculative` |
| `contradictions` | 来源之间的矛盾 |
| `open_questions` | 未回答问题 |

三个操作：**ingest**（一次摄取可连锁更新 10–15 页）、**query**（带引用作答）、**lint**（坏链、矛盾、孤儿页、过时内容）。设计动机是「编译一次、持续维护」，替代「每次查询都从原始切片重新推导」的 RAG。

### 4.2 规范里明确缺失的部分

WikiHub《The LLM Wiki Format》是唯一把它写成文的一页，它自己承认没有定义：

- 用户角色（管理员 / 编辑 / 读者）
- 页面级或目录级 ACL
- 编辑审批与审核流
- 多人并发编辑的冲突解决
- 页面署名与所有权转移
- 团队协作工作流

它只有 `public` / `private` 与 frontmatter 的 `visibility`，那是 WikiHub **平台层**附加的，格式本身不含。另有实践文章建议「注册 raw source 时要带 permissions 字段」，属于工程建议，不是规范内容。

**判断**：LLM wiki 的默认假设是「单人或小团队、内容全公开、靠 Git 历史兜底」。企业场景下权限是一块空白，没有现成答案可抄。

## 5. 与本平台现状的对照

### 5.1 已实现的部分（`internal/tool/wiki.go`）

| 维度 | 现状 | 评价 |
|---|---|---|
| 宿主 | 固定系统空间 `files/wiki/`，工具参数无 space 维度（`wikiKey` 只读 `env.WikiSpaceID`） | 符合「容器优先」，比页级 ACL 更易治理 |
| 分区 | 再按智能体切成 `files/wiki/<智能体 slug>/`：`wiki_*` 的 `path` 一律相对该目录，读写只看得到自己那份（`env.AgentID` 由会话绑定的智能体注入，未绑定落 `base`） | 容器边界与写者对齐，不需要逐次判定 |
| 宿主注入 | 会话创建时由服务端注入 `WikiSpaceID` 与 `AgentID`，任一缺失则明确报不可用，不回落当前空间 | 正确，避免知识分裂 |
| 路径约束 | `cleanRelPath`（绝对路径 / `..` / 平台保留的隐藏项，用户自己的隐藏页面放行）+ 最多 3 层 + 只允许 `.md` + 单页 128KB | 到位 |
| 读 | 空间成员即放行（`RiskReadOnly` + `read-only`） | 缺分类可见性 |
| 写 | `RiskWrite` + `SideEffectsShared`；当前空间 `write` / `manage` 放行，**不转审批** | 缺节点级控制，任何有写权限者可改全局公共知识 |
| 与 `file_*` 的隔离 | `file_list` / `file_read` / `file_write` 遇到 `wiki/` 前缀直接拒绝并改道 | 到位 |
| 撤销 | 依赖空间成员关系，即时生效 | 优于文档级 ACL 的同步窗口 |

### 5.2 差距

| 差距 | 具体表现 | 严重度 |
|---|---|---|
| **无节点级权限** | 粒度停在智能体分区：同一个智能体目录内仍是全可读 / 全可写，没有按页面区分 | 中（智能体之间已隔离） |
| **`list` / `search` 是泄露面** | `wiki_list` / `wiki_search` 已按智能体目录收敛，但目录内仍返回全部页面路径与命中行 | 中（一旦加页级权限立刻暴露） |
| **审计粒度不足** | 工具调用经 `Invoker.finish` 统一落 `tool:invoke` 审计与 `tool_call`，但 `Args` 固定为 `{}`、`detail` 只有 tool / status / latency / risk，**看不出写了哪一页、改前改后是什么** | 中 |
| ~~**技术方案与实现脱节**~~ | 已收口：`llm_wiki` 资源与 `resource_grant` / `tool_binding` 一并下线（`0024_drop_resource.sql`、`0028_drop_tool_binding.sql`），《技术方案》§5.5 已改为「插件安装即授权」 | 已解决 |
| **无审批与并发以外的冲突治理** | 已有 `if_version` 冲突检测与进程内互斥，但没有编辑审批；多实例下 `overwrite` 仍可能丢更新 | 低 |

已有的一致性机制（无需重做）：`contentVersion` = 内容 sha256 前 8 字节，`overwrite` 带 `if_version` 冲突即拒绝并提示重读；`append` 天然无冲突；同进程按存储 key 串行。

## 6. 演进路线

两条路线（C 已作废，见下），代价递增，**建议先做 A，把 B 作为 B 阶段的目标**。

### A. 容器分区（已落地，按智能体切）

把 `wiki/` 切成 `wiki/<智能体 slug>/`，`path` 相对该目录，工具只读写自己那份（宿主仍是系统空间，跨空间共享但不跨智能体）。原方案里的「按 domain 绑定宿主空间」没有采用：知识的归属天然是「哪个智能体在写」，按 domain 分反而要多维护一张 domain → 空间的映射，也解释不了「同一批人在两个智能体上口径不同」。

- 符合飞书知识空间 / Confluence space / 容器化 RAG 的共识：**权限边界与存储容器对齐，检索侧不做过滤**。
- 零查询过滤、零漂移、权限变更即时生效。
- 代价：粒度只到智能体级；跨智能体共享同一份知识需要人为复制或另立一个公共智能体。

### B. frontmatter 早期绑定（节点级）

页面头写 `visibility: org | space:<id>`（或 `readers: [...]`），在 `wiki_read`、`wiki_list`、`wiki_search` **三处统一**过滤。

必须同时满足的三条，否则等于没做：

1. `list` / `search` 与 `read` 用同一套判定函数，不允许各自实现。
2. 子页面只能收紧不能放宽，且不得超出父级上限（照抄飞书的继承规则，别踩 Confluence 的坑）。
3. 冲突时以父级为准，并在工具返回里说明被收紧的原因，避免模型反复重试。

### ~~C. 资源化~~（已作废）

资源模型已整体下线：`resource` / `resource_grant` / `tool_binding` 都不存在，`llm_wiki` 也不作为资源存在。知识库只保留 A / B 两条路线，权限边界靠容器（domain）或 frontmatter 表达，不依赖平台级资源授权。

### 无论走哪条都必须补的两件事

1. **内容级审计**：`wiki_write` 记录 `path`、`mode`、`version` 前后值。当前只到「调用过 wiki_write」这一层，出事查不出改了哪页。
2. **`list` / `search` 的可见性过滤**：这是知识库最安静的泄露通道。

### 明确不建议

- **不做 chunk 级 ACL**：wiki 是页级 markdown，量级远小于 RAG 索引，也不存在向量库；引入 chunk ACL 只会带来查询过滤与 payload 重写的全套问题。
- **不做运行时回源校验**：我们的知识本体就在平台自己的存储里，没有需要回源的外部系统。

| 1 | wiki 的权限边界应该是「域」还是「页面」？域级改动小但与协作习惯冲突 | 决定走 A 还是 B |
