## 0. 一句话定位

**WorkAgent 是企业级 Agent 工作台**：Agent 以用户身份在真实文件空间里执行，能力以插件形式开发、发布、安装，执行跑在沙箱内——解决的是通用助手「进不了内网」、低代码平台「流程要先搭」这两类问题。

| 维度 | 事实 |
|---|---|
| 角色 | Agent 运行时负责人 / 核心开发（按实际改） |
| 技术栈 | Go 1.23（后端）、React 18 + TypeScript + Vite（前端）、Deno（插件脚本运行时）、PostgreSQL 16 |
| 规模 | Go 约 4.5 万行、TS 约 8 千行、30 个 DB 迁移、25 个内部模块、唯一直接第三方依赖 `pgx` |
| 能力域 | LLM Harness、上下文工程、插件运行时与沙箱、权限与审批、MCP、混合搜索、Agent 评测 |

## 1. 简历精简版（可直接粘，5 行）

**WorkAgent — 企业级 Agent 平台（Go / React / Deno）**｜Agent 运行时负责人

- 自研 LLM Harness：可替换编排契约（内置 ReAct / 无工具直答 / 预留 Eino 适配），平台侧统一提供预算、审批挂起、checkpoint 续跑、上下文压缩，框架类型不出模块边界。
- 上下文工程三层：跨轮「摘要 + 向量召回 + 滑动窗口」、轮内「丢过程留结论」的确定性压缩（不调模型、零失败成本），单轮工具循环默认 40 轮、连续 2 轮无新信息强制收尾。
- 工具调用可靠性：按调用指纹去重（同工具同参数第 3 次拦截），进度守卫用可观测事实而非额外模型调用判断「有没有进展」，长任务从「预算耗尽返回空」变为稳定产出结论。
- 权限与审批：授权只有「插件安装」一条路径；审批按动作类别判定，只对出网非只读、远端写、高危命令人工确认，其余自动执行并留风险徽标供事后 review。
- 建立 Agent 行为评测：`evals.json` 脚本化模型回合重放，断言停止原因与工具调用序列；确定性用例进发布门禁，行为用例进 CI，规避 LLM-as-judge 的抖动。

## 2. 简历完整版（项目经历展开）

### 2.1 项目背景

企业内网的 Agent 平台。目标不是「能聊」，而是 Agent 能接进真实业务：以用户身份执行、工具按清单授权、高危动作审批、执行在沙箱内。

技术难点集中在 Harness——如何让模型在 40 轮工具循环里不跑偏、不失忆、不烧穿预算、失败可恢复；以及如何让「授权」在结构上没有中间态。

团队的取舍是：**流程从对话和文件里长出来，而不是先画图**。技能、工具、MCP、UI 组件、智能体统一为插件，走同一条「开发 → 发布 → 安装 → 运行 → 卸载」链路。

### 2.2 我负责的部分

#### 1）Harness 分层与可替换编排

- 定义 `agent.Agent` 契约，用 `Capabilities`（tools / parallel_tools / streaming / reasoning / approval / resume / dispatch / guard）声明实现能力，上层按能力降级并向客户端说明，而不是假设所有实现都支持。
- 三种实现：内置 ReAct 循环（默认）、无工具单轮直答（轻量路径）、预留 Eino 适配（唯一允许 import 框架的子包）。
- 关键约束：**框架类型不出模块边界**。Run 状态机、预算、审批、checkpoint、上下文压缩全部平台自研，换编排框架不需要动业务层。

#### 2）上下文工程（Context Engineering）

- **跨轮三段式组装**：长期摘要（更早消息压成事实性摘要）+ 按需向量召回（用本轮 query 补齐摘要遗漏的细节，cosine 阈值 0.35、TopK 4）+ 最近 16 条原文滑窗；按 token 预算控制（默认 24000 字窗口），不按字节截断。
- **轮内压缩**：一轮长任务里 messages 会随工具回执线性膨胀且每轮重发，撞窗口不是降级而是整轮报错。做法是「丢过程、留结论」——较早的工具往返折成进展记录，保留系统提示词、最近 3 轮原始回执、每轮已对用户说过的内容；已撞窗口时走紧急档（只留 1 轮）。
- **关键取舍**：压缩不调模型。判决与摘要都是确定性的，零失败、零额外成本，否则压缩自身会成为新的故障点。

#### 3）工具调用可靠性（长任务不跑偏）

- 进度守卫每轮回答三个问题：这一步有没有带来新信息、下一步还有没有价值、该不该强制收尾。判断全部基于调用指纹与结果摘要，**不额外花一次模型调用**。
- 同工具 + 相同参数第 3 次起直接拦截并回填固定标记（第 2 次仍放行——模型换问法前重试一次是合理的）；连续 2 轮无新信息则收回工具、要求模型用现有信息作答。
- 收尾策略上只「收回工具」不「终止循环」：终止的代价必然是用户收到一条空回答，强制收尾还有机会拿到结论。
- 支持同一轮多工具并行、reasoning 过程透传、SSE 流式增量。

#### 4）多 Agent 协作

- 把子 Agent 做成**工具**（`agent_dispatch`）而不是编排图：主 Agent 决定何时整件事交出去，子 Agent 复用同一套工具链、策略与审计，但上下文与预算隔离。
- 约束参数化：子任务默认 3 轮（比主任务窄，避免跑偏代价放大）、结论回填上限 4KB（必须自包含，不搬过程）、派发深度默认 2 层。
- 子 Agent 有独立追加提示词：直接做、不扩范围、缺信息就说明缺什么；工具集合只能是父集合的子集，权限仍在叶子调用上判定。

#### 5）多模型路由与成本

- `Route = Primary + Fallbacks + Model 覆盖 + Required 能力标签`，三条路由 `chat` / `summary` / `embedding`；摘要与轻量任务走小模型。
- 降级有硬约束：只有协议族一致（schema 兼容）才降级，否则报错而非静默降质；流式已向前端输出内容后不再降级，避免重复文本。
- OpenAI / Anthropic 双实现，Provider 抽象 + Router 统一流式回调。

#### 6）Agent 安全与评测

- **提示词分层**：平台基础规则写死、智能体只能追加不能覆盖（base 锁定），再叠加会话选中技能正文（4000 token 预算）与平台部署事实。
- **能力按需检索**：平台不提供全量技能列举，系统提示词只写「何时必须检索」的硬规则，正文由 `plugin_search` / `plugin_read` 按需拉取，避免索引被截断并挤占对话空间。
- **评测双轨**：`evals.json` 里 `kind=tool` 确定性用例（无需模型，进发布门禁强制跑）、`kind=agent` 行为用例（脚本化模型回合重放，断言停止原因与工具序列）。
- 选择脚本回放而非 LLM-as-judge：Harness 行为（何时收尾、何时拦截、派到第几层停）必须可复现，评委模型本身就是不稳定源。

#### 7）权限与审批（Agent 落地最关键的一块）

- **授权只有一条路径**：插件安装 / 启用即授权。工具能出现在空间的工具列表里，就说明所属插件已装好，这个动作本身就是授权，没有额外的资源层或绑定层记录。
- **审批按动作类别判定**：只有三类需要人确认——出网非只读（清单 `verbs` 含 GET/HEAD 之外的动词）、MCP 显式声明 `tools.writes`、shell 命中「需确认命令」名单（`rm` / `dd` / `chmod` 等，动态形态如 `$(...)`、反引号、`xargs`、`sh -c` 一律命中）。
- **风险等级用于展示，不参与判定**：卡片头给文案徽标（只读 / 查询 / 写入 / 高危，不显示 L1–L4 编号），`tool.call` / `tool.result` 事件带 `risk`，历史消息从 `run_step.risk` 还原，因此不审批的调用也能看出这一步动了什么。
- **判定依据**：等级 × 副作用需要人做二维推理，实际效果是用户对每一次写都点同意，审批退化为形式；而 fs 写的范围被工具锁死在当前空间工作区（工具不接受 `space_id` 参数），删错还有回收站与审计。审批只留给「不可逆且平台无法替代用户判断」的动作。
- **MCP 的「是否写」只能靠声明**：远端 server 对平台是黑盒，只有 `input_schema`，看不到实际请求，从动词推导不成立，因此由作者声明 `tools.writes`，未声明按只读处理；同时用 `tools.allow` 白名单，不默认信任远端暴露的全部工具。
- **审批是持久化事实，不是内存状态**：`approval` 表一行一次调用，`pending → approved / denied / expired`；按 `run_id` + `action_key`（本轮同类动作）+ `args_hash`（同一次调用）复用已决结论。刷新或换标签页能按 `session_id` 补回卡片，进程重启后同一动作不会被重复询问，多副本下决策先落库、等待方 2s 轮询收敛；超时 5 分钟按拒绝处理但不中断 run，没有审批通道时默认拒绝。

#### 8）支撑能力（一句话级）

- 工具执行在 Deno 沙箱（Linux `bwrap` / macOS `sandbox-exec`），默认 `--unshare-net`；出网走每插件实例独立的 unix-socket 代理 + 清单白名单；文件权限由「挂载决定路径在不在」与「Deno 权限决定允不允许读」双重收口。
- 凭证信封加密（KEK 包裹每条凭证独立 DEK，AES-256-GCM），对外只暴露 8 位指纹，模型上下文与审计日志永不含明文。
- 插件脚本默认一次性进程，声明 `runtime.resident` 才按「空间|slug|目录」复用，空闲回收；安装/升级/停用/卸载立即杀进程。

## 3. 对比亮点表

### 3.1 Agent 技术维度

| 业界常见做法 | 本项目的做法 | 为什么更好 |
|---|---|---|
| 用 LangChain / LangGraph 的 AgentExecutor，框架类型渗进业务层 | 契约层不出现框架类型，Run 状态机 / 预算 / 审批 / checkpoint / 压缩平台自研，编排实现可替换 | 踩到框架坑能换实现而不重写业务；LangChainGo 已停止维护，该风险被隔离在一个子包 |
| 靠 prompt 写「不要重复调用工具」 | 调用指纹去重（第 3 次拦截）+ 停滞计数强制收尾，判断不花模型调用 | 约束从「请求模型配合」变成「机制上保证」，且零额外成本 |
| 撞上下文窗口就报错，或粗暴截断整段 | 轮内确定性压缩（丢过程留结论）+ 跨轮摘要 / 召回 / 滑窗三段式 | 40 轮长任务不断线，压缩自身零失败成本 |
| 上下文按条数或字节截断 | 按 token 预算组装，读类工具可申请 24KB 回填 | 不丢指代与语气连续性，长会话不线性膨胀 |
| 模型挂了直接重试，或降级到任意模型 | 只有协议族（schema）兼容才降级，流式已出内容不再降级 | 避免「静默降质」与「前端看到重复文本」两类线上事故 |
| 多 Agent 用图编排表达 | 子 Agent 是工具：上下文与预算隔离、结论 4KB 自包含回填、深度与轮次硬约束 | 中间输出不污染主上下文，成本可预测，实现复杂度低一个数量级 |
| 评测靠 LLM-as-judge 打分 | 脚本化模型回合重放，断言停止原因 + 工具序列；确定性用例进发布门禁 | 行为回归可复现，不受评委模型自身漂移影响 |
| 通用 Agent 产品（AutoGPT 类）无权限、无沙箱 | Agent 以用户身份执行、工具按插件安装授权、执行在沙箱 | 企业内网可落地，越权在机制层不成立 |

### 3.2 权限与审批维度

| 业界常见做法 | 本项目的做法 | 为什么更好 |
|---|---|---|
| 每个写操作都弹确认 | 只对不可逆且平台无法替代用户判断的动作审批 | 规避审批疲劳——高频确认会让用户闭眼点同意，等于没有审批 |

## 4. 面试深挖：问题 → 做法 → 收益

### 4.1 「模型 40 轮还在原地打转，最后用户收到空回答」

- **现象**：轮次上限调到 40 后，失败的主因不是轮次不够，而是循环在做无用功——同工具同参数反复调、每轮拿空结果、写完文件又读回来确认。
- **做法**：调用指纹 + gain / stalled / ForceFinal 三问；只收回工具，不终止循环。
- **收益**：长任务从「预算耗尽」变成「用现有信息给出结论」，且判断不额外消耗模型调用。

### 4.2 「一轮里工具回执把上下文顶爆」

- **现象**：每轮把整份 messages 重发给模型，长任务下线性增长，撞窗口是模型直接报错、整轮失败。
- **做法**：折叠成进展记录，保留系统提示 + 最近 3 轮原始回执 + 每轮已对用户说过的内容；紧急档只留 1 轮。
- **收益**：压缩确定性、零模型调用，越界不再导致整轮失败。

### 4.3 「Harness 改了不知道有没有改坏」

- **做法**：`evals.json` 双类用例。确定性用例无需模型，进发布门禁；行为用例脚本化模型回放，断言停止原因与工具序列。
- **收益**：Harness 行为可回归，且发布门禁不依赖外部模型可用性。

### 4.4 「为什么不是每个写操作都审批」

- **判断**：审批的价值在于「不可逆 + 平台无法替用户判断」。空间内写的范围被工具自己锁死，删错有回收站和审计，不需要人看；把这类动作也弹窗，会让用户对确认框脱敏，真正危险的出网写反而被淹没。
- **做法**：判定降成一维——只看出网动词、MCP 的 `tools.writes`、命令名单；等级退成展示徽标，让不审批的调用也能看出动了什么。
- **收益**：确认次数集中在真正需要判断的动作上，同时事后 review 的信息更完整。

### 4.5 「审批等人，进程挂了怎么办」

- **做法**：审批落 `approval` 表，等待期间 run 落 `waiting_approval`（可恢复状态而非终态），每 30s 续心跳避免被 idle 看门狗判定卡死；批准时先试本进程唤醒通道，执行体已死则从断点续跑，该动作按 `args_hash` 复用「已批准」，已完成的工具调用靠结果回放而不重跑。
- **收益**：刷新页面能补回卡片，重启不丢结论，多副本下库是唯一真相。

## 5. 表述口径（按当前实现写，别写错）

| 事项 | 当前口径 | 代码位置 |
|---|---|---|
| 空间权限 | `space_member.perm` 取值 view / read / write / manage；判定只用两档：只读（view、read）、可写（write、manage）；`manage` 管发布 / 安装 | `internal/policy/policy.go`、`internal/space/service.go` |
| 审批触发 | 只看动作类别：`net.write`（出网非 GET/HEAD）与 `shell`（命中命令名单）；MCP 看清单 `tools.writes` | `internal/policy/policy.go`、`internal/tool/approval.go` |
| 风险等级 | 只用于展示徽标与事后 review，不参与审批判定 | `internal/policy/policy.go` |
| 授权模型 | 只有插件安装 / 启用一条路径，没有资源层与工具绑定 | `internal/plugin/manifest.go` |
| 身份与管理权 | 身份来自钉钉；系统管理员由 `ADMIN_JOB_NUMBERS` 配置指定，没有组织级角色表 | `internal/identity/`、`internal/space/system.go` |
| 审批记录 | `approval` 表，状态 pending / approved / denied / expired，`scope` 只有 once / turn | `internal/store/postgres/migrations/0029_approval.sql` |

**易误写点**：

1. 不要写「四级权限 view / read / write / manage」——判定实际是只读 / 可写 / 管理三档。
2. 不要写「L1/L2 放行、L3 按空间权限、L4 一律审批」——风险等级不参与审批。
3. 不要写「实现组织架构管理与 RBAC」——没有组织级角色表，权限是空间成员制 + 管理员配置。
