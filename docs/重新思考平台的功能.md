# 企业级 Agent 平台
生产力的提升，能够带来极大的物质丰富，比如 AI 让优良的影视剧出现极度丰富。那么原来很多比较贵的服务，中小企业无法享受的服务，比如专业的视频制作、文案、咨询服务、定制化软件等，现在可以通过 Agent 来实现。所以我希望实现一个可以让 Agent 自己创建各种场景的智能体和软件的平台。

# 需要你帮我做的事情
1. 结合这个需求背景，再深入调研目前市场上具体的需求场景
2. 结合调研的需求场景，设计出一个产品形态，并给出产品功能的详细设计，可以摒弃原有不合理的产品形态，重新设计一个全新的产品形态
3. 给出技术方案设计
4. 制定一个计划

# 延伸思考

上面的四件事是「怎么做」，但在动手前还缺三样东西：**假设拆解、内部一致性、成功度量**。以下是把愿景往下推一层的结果，作为后续调研与设计的输入。

## 1. 把愿景拆成可证伪的命题

原文的推理链是：`生产力提升 → 物质丰富 → 贵服务变便宜 → Agent 承接这些服务 → 做一个人造 Agent/软件的平台`。

前三步是宏观判断，**第四步才是产品命题**，而且中间少了一个关键推导：

> 贵，到底贵在哪里？

拆开看，这类服务的高定价并不来自「知识本身」，而来自三样东西：

| 成本项 | 含义 | Agent 能否压低 |
|---|---|---|
| **(a) 稀缺专家的时间** | 一个懂行的人 × 若干小时 | 能，且降低一个数量级 |
| **(b) 行业流程与模板的沉淀** | 反复调试出来的方法、checklist、素材库 | 只有平台具备沉淀机制才能 |
| **(c) 交付责任与信任背书** | 交付出错谁担责、客户凭什么相信 | 基本不能，必须由人担保 |

所以平台的真实命题不是「让 Agent 做服务」，而是：

> **把 (a) 的成本降一个数量级，同时让 (b) 每交付一次就沉淀一层、下一次更便宜，并把 (c) 变成可交给人审的流程。**

推论：如果 (b) 不成立，每次交付都是从零开始的对话，边际成本不下降，平台会退化成一个「更好的 ChatGPT 入口」。因此这个平台的第一指标不是 Agent 数量、不是 DAU，而是**资产复用率**。

## 2. 产品内核：必须是一个双循环

```
需求 → Agent 组装能力 → 交付物 → 用户验收
              ↑                      ↓
        资产库（技能/工具/组件/智能体）← 沉淀（人审后固化）
```

- **左环（生产）**：对话即开发。用户只说需求，Agent 在资产库里检索、组合、补齐缺失件。
- **右环（沉淀）**：交付完成后，把新写的提示词、工具封装、UI 组件、数据契约**固化成插件入库**。这是把「(a) 便宜」变成「(b) 也便宜」的唯一机制，也是最容易被忽略的一半。

现状评估：右环的技术底座已经具备（六类 `kind` + 发布快照 + 市场 + 安装副本 + DSL 组件），缺的是**产品流程上的强制动作**。目前交付完就结束了，没有「把这次产出存成可复用包」这一步。建议做成显式动作，例如：「本次交付已沉淀 3 个技能，是否命名并发布到市场？」

## 3. 最尖锐的矛盾：企业级假设 vs 无 IT 的中小企业

现有实现（`AGENTS.md`、`internal/*`）建立在一个明确假设上：**存在系统管理员、有审批流、有组织架构、有工号**。发布权归系统管理员、L4 需审批、密钥由管理员在系统空间录入。这套设计对中大企业是正确的。

但本文的愿景面向的是**中小企业**——没有 IT、没有管理员，老板自己就是管理员。两者冲突：

| 维度 | 企业形态（现状） | 中小企业形态（愿景） |
|---|---|---|
| 管理员 | 独立角色，走流程 | 就是老板本人 |
| 审批 | L3/L4 分级审批 | 无审批，但要「事后可解释」 |
| 发布权 | 系统管理员集中发放 | 谁做的谁发，用安装量过滤 |
| 信任来源 | 组织内身份 + 审批 | 沙箱隔离 + 来源标记 + 使用数据 |

**这个岔路必须在设计前定下来**，优先级高于任何功能细节。三个选项：

1. **只做企业**：砍掉本文的中小企业叙事，愿景改为「组织内生产力平台」。
2. **双形态**：同一内核，两套治理策略（企业开审批、中小企业降级为事后审计）。
3. **中小企业优先**：现有审批链降级为可选能力。

倾向第 2 个，但需要在文档里写清楚。否则后续每条功能都会在两套假设之间反复摇摆。

## 4. 重新定义产品单元：交付包，而不是 Agent，也不是 App

现有六个 `kind` 是**零件**，而用户要买的是**成品**。缺少一层「应用 / 交付包」的定义：一个具名、有版本、有输入输出契约、可一键运行的组合体。

```
交付包 = 智能体（行为）
       + 技能（流程）
       + 工具 / MCP（能力）
       + 组件（界面）
       + 资源引用与权限清单
       + 验收标准
```

有了这一层，才能回答三个问题：用户在市场上「装」的到底是什么、卸载时带走什么、它被允许碰哪些数据。

DSL 组件已经把界面变成声明式的（没有 JS/HTML/CSS 注入点），方向正确；但**应用的运行时**仍是空白：前端静态托管或 CDN 同步、后端容器 / 长驻进程 / 长连接（IM 类插件要引厂商 SDK）、平台注入 token、域名统一走网关代理、出网白名单。这是从「能对话」跨到「能交付软件」的门槛，建议单独立项，不要塞进插件体系内部消化。

## 5. 六个必须提前回答的硬问题

1. **质量由谁担保**：技能本质是提示词，会随模型升级而退化。没有 golden set + 回归评测，第二次交付可能不如第一次。评测集应作为资产的组成部分随版本发布，而不是运营动作。
2. **数据边界**：客户的合同、财报、内部系统数据从哪进来、能不能出网、要不要私有化部署。直接决定搜索源的 `endpoint` 白名单、私网策略、以及是否可以只用公有云。
3. **责任归属**：Agent 写错一份投标文件，谁承担？因此「人审节点」必须是产品里的一等公民，而不是事后审计日志。
4. **第三方资产的可信度**：市场里的插件谁敢装？现有权限清单、沙箱、风险推导（`Derive`）是基础，但缺签名与来源可信链。
5. **成本不可控**：长任务与多轮工具调用的 token 成本可能超过服务售价，越成功越亏。需要 run 级成本账本与配额，并按交付物而非 token 计费。
6. **进入既有工作流**：老板买了、员工不用等于零。入口要长在钉钉 / IM / 浏览器 / 邮件里，而不是再造一个「平台网站」让用户主动访问。

## 6. 对现有形态的取舍

- **保留**：空间作为隔离与权限边界；插件作为唯一资产格式；市场作为分发面；DSL 组件（放弃 iframe 与代码注入是明智的）。
- **收敛**：「资源发布（`/resources/snapshots`）」与「插件发布 / 安装」目前是两套语义相近的机制，长期会造成认知过载。建议统一到插件，把资源发布降级为插件的可见性属性。
- **别做**：让 Agent 自由生成代码、自由连数据库、自由出网。「Agent 造软件」必须收在声明式组合与沙箱之内，这条底线比功能完整性更重要。
- **补上**：§2 的右环（沉淀动作）、§4 的交付包与运行时、§5 的评测与成本账本。

## 7. 建议补一个「第 0 步」：成功度量

上面的四件事（调研、产品形态、技术方案、计划）都缺一个基准。先定三个数，否则形态与范围无法裁剪：

| 指标 | 定义 | 初期目标 |
|---|---|---|
| 交付成本收敛比 | 同类需求第 3 次 / 第 1 次的交付成本 | ≤ 0.3 |
| 资产复用率 | 新交付中直接复用的插件占比 | ≥ 50% |
| 人审耗时占比 | Agent 产出到可用之间的人工分钟数 / 总工时 | ≤ 30% |

有了度量，再选**一个垂直场景端到端跑通**证明边际成本递减，然后才谈平台化。候选场景按「可验证性 × 风险」排序：

1. **内容类**（短视频脚本 → 分镜 → 成片流程、品牌物料、文案）：风险最低、验收标准直观，适合先跑。
2. **文档 / 咨询类**（研究报告、投标文件、合规审查）：可验证性中等，价值高，需要知识库与引用可信度。
3. **定制软件类**（内部小工具、轻应用）：价值最高、风险最高，依赖 §4 的应用运行时。

结论：先做内容类验证双循环，同时并行设计应用运行时；在双循环被证伪前，不要投入做大而全的市场运营。
