# 编程实践

写、改、调试、重构、审查代码时的统一工作方法。核心只有一条：**改动必须可验证**。

## 什么时候用

用：

- 要改空间文件区里的代码或脚本（插件脚本、`.ts` / `.js`、配置）。
- 修一个具体的 bug、补测试、重构、做代码评审、跑命令验证结果。

不用（直接回答，不要检索本技能）：

- 解释一段代码为什么这么写、回答语法 / API / 库用法。
- 给一段示例代码、把已有代码翻译成另一种语言、只改注释或命名。
- 只讨论方案、不落地改文件。

拿不准时按「会不会动文件」判断：会动就用，纯回答就不用。

## 能力边界（先认清再动手）

| 位置 | 能做什么 |
|---|---|
| 当前空间 `files/` | `file_list` / `file_read` 读；`file_write` 写 md / json / txt / yaml / ts / js，单文件 ≤256KB，**单次 content ≤12KB**（更大就分块 `append`） |
| 沙箱命令 | `shell_exec` 跑 `sh -c`：只有空间目录可写、**默认无网络**、默认 15s（最长 25s）、输出上限 16KB |
| 用户本地仓库 | 看不到、改不了：只给 diff / 补丁与操作步骤，并说明「需要你在本地应用」 |

其它后缀（`.go` / `.py` / `.java` / `.sh` …）`file_write` 会拒绝，只能用 `shell_exec` 生成或让用户本地改。

## 工作流

1. **读**：`file_list` 找到位置，`file_read` 读到改动点前后足够的上下文。没读过就不改。
2. **定验收**：动手前明确「怎么算改对了」——一条命令、一份对比输出或一张检查清单。说不清就先问需求。
3. **最小改动**：一次只做一件事，只碰与目标相关的行；格式、改名、依赖升级另开一轮。
4. **验证**：跑第 2 步的验收，保留真实命令与输出。失败就缩小范围重来，不要换参数重跑同一条。
5. **报告**：改了什么（路径 + 一句话原因）、怎么验证的（命令 + 关键输出）、哪些没验证、下一步建议。

## 硬规矩

- **证据优先于声明**：没跑过就说没跑过，「应该能跑」「理论上没问题」不算验证。
- **不猜 API**：不确定签名 / 字段名时先读调用点与类型定义，再查官方文档；查不到就标「待确认」。
- **不重复失败**：同一条命令同参数第二次结果一样；连续两次失败就换假设（读代码 / 加日志 / 缩小复现）。
- **不整文件重写**：`file_write` 是覆盖语义，写之前必须 `file_read`；只改必要部分。
- **不越权**：只写空间内的相对路径；不要 `../`、绝对路径、`sudo`、装系统包。
- **大改动先给计划**：超过 3 个文件或要动结构时，先列步骤让用户确认。

## 坑

- `file_write` 报「仅支持 md / json / txt / yaml / ts / js」：不是权限问题，是后缀限制，改走 `shell_exec`。
- `file_write` 报「参数被截断」：内容超了模型单次输出上限，不是文件大小超限。把正文切成 ≤12KB 的块，第一块 `mode=overwrite`、其余 `append` 追加到同一路径。
- 沙箱无网络：`npm install` / `pip install` / `git clone` 必然失败，别当成环境坏了反复排查。
- `shell_exec` 单次 15s：全量测试、大范围 `find`、`sleep` 容易超时，用过滤条件或分批跑。
- 输出超 16KB 会被截断：测试日志先 `| tail -n 40` 或 `| grep -E "FAIL|Error"` 再回填。
- 子 Agent（`agent_dispatch`）看不到本会话：派发时把文件路径、目标、验收标准写全。
- 审查 ≠ 修改：用户只让评审就只出清单，改动另开一次确认。
