# 调试（修一个具体问题）

四阶段，不要跳步。

## 1. 复现

- 拿到最小可复现输入：一条命令、一份数据、一段配置。复现不了就先补信息（日志、版本、输入样本），**不要凭猜测改代码**。
- 记录三件事：期望行为 / 实际行为 / 触发条件。写不出来说明还没定位到问题。

## 2. 定位（找根因，不是找「改了就好了」）

- 读错误来源：堆栈第一行通常不是原因，顺着调用链读到自己代码里那一行。
- 二分缩小：注释掉一半、加一行日志打印中间值；每次只加一处探针，跑完就撤。
- 先立假设再验证：写出「如果 X 是原因，那么 Y 应该成立」，再去验证 Y。不要一边猜一边改。

## 3. 简化

- 把复现压到最小：去掉无关输入、无关分支、无关依赖。
- 最小复现能贴进一个文件时，问题通常已经清楚了。

## 4. 修复

- 改根因那一处，不是改调用方绕过它。
- 补一条回归用例：修复前失败、修复后通过。没有用例的修复等于没修。
- 修复后重跑复现步骤，并验证相邻功能，确认没有连带破坏。

## 禁止

- **试错式乱改**：连续两次「改了没效果」就停下来重新读代码，不要第三次换个写法再试。
- **把报错藏起来**：加 `try/catch` 吞异常、放宽校验、忽略返回码，等于把 bug 换成静默失败。
- **一次改多个地方**：即使最后好了，也不知道是哪一处的功劳，也没法回滚。

## 平台限制

- 默认没有网络：拉不到依赖、查不到远端日志。确实要联网就声明 `need_network=true`（含 curl 等会先弹确认）；查外部信息用 `web_search`，别指望 `curl`。
- 单次命令 15s：卡死或长轮询的复现要加超时参数（`timeout` 命令不可用时靠 shell 的参数）。
- 改完必须能复跑同一条复现命令，把命令与输出一起给用户，别只给结论。

## 报告

- 根因一句话：哪个文件、哪一行的什么假设不成立。
- 修复方式与为什么这样修（而不是换个写法绕过）。
- 验证：复现命令现在的输出、回归用例。
- 同类风险：还有哪些地方有相同写法，建议一起排期。
