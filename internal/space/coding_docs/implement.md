# 实现（新功能 / 新脚本）

## 开始前

- 先问清三件事：输入是什么、产出给谁用、有没有外部副作用（写库 / 发消息 / 花钱）。缺关键信息一次问完。
- 先在空间里找同类实现：`file_list` + `file_read`。有既有约定（命名、目录、错误处理）就沿用，不要另起一套。
- 定验收：一条能跑的命令、一份能对比的输出、或一张检查清单。写不出验收条件，说明需求还没清楚。

## 实现顺序（一次一小步）

1. 先让最窄的一条路径跑通：一个输入、一条分支、一个输出。
2. 再补分支与异常：空输入、超大输入、上游失败、权限不足。
3. 最后才做抽象：出现第二处相同逻辑时再抽函数，不要提前设计框架。
4. 每步都跑一次验证，不要攒到最后一次性调试。

## 测试先行（RED → GREEN → REFACTOR）

适用：逻辑能被纯函数或脚本覆盖、改动会被反复运行（插件工具、脚本型搜索源、数据处理）。
不适用（说明理由，别硬套）：一次性脚本、纯配置或文档改动、验证成本明显高于收益的场景。

1. **RED**：先写一条会失败的用例，并真跑一次确认它失败——失败原因必须是「功能没实现」，不是用例写错。
2. **GREEN**：写最小实现让它通过，不加用例没要求的功能。
3. **REFACTOR**：测试全绿后清理重复与命名；一次只做一个变换，跑完再下一个。

## 平台限制

- 空间里能直接写的是 md / json / txt / yaml / ts / js（`file_write`，单文件 256KB，但**单次 content 别超 12KB**：模型单次输出有上限，超了会被截断成半截 JSON）。更长的文件分块写：第一块 `mode=overwrite`（新文件 `create`），其余 `append` 追加到同一路径。`.go` / `.py` / `.sh` 等后缀要用 `shell_exec` 生成，或让用户本地改。
- `shell_exec` 没有网络：依赖装不上。要跑测试先确认运行时与依赖已经在环境里（`which node`、`ls node_modules`），没有就直说「本环境跑不了」，并给出用户本地可执行的验证命令。
- 单次命令 15s、输出 16KB：测试用 `--filter` / `--grep` 缩小范围，日志用 `| tail -n 40`。

## 产出格式

- 新增 / 修改的文件路径 + 一句话作用。
- 关键决策：为什么这么选、备选是什么、为什么没选。
- 验证命令与结果（原样贴关键输出）。
- 未覆盖的部分与建议的下一步。
