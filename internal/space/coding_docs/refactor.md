# 重构（行为不变地改结构）

## 前提

- **必须有测试基线**：改动前把所有相关验证跑一遍，记下通过状态。没有测试就先补最小验证手段（对比输出、金标准文件、校验脚本）——跑不了验证就别重构。
- **说清目标**：可读性 / 去重 / 解耦 / 换实现。目标不明确的重构最后都变成重写。

## 步骤

1. 先固化当前可运行状态：让用户提交一次，或在空间里 `file_write` 一份备份（如 `xxx.bak.md`），并告知用户。
2. 每次只做**一个机械变换**：改名 → 跑验证；提函数 → 跑验证；换数据结构 → 跑验证。
3. 一次变换一次验证，红了立刻回退，不要「攒几个改动一起看」。
4. 全部完成后对比行为：同一组输入的输出必须一致；时间戳、顺序不稳定的字段先归一化再比。

## 红旗（出现就停手）

- 需要同时改测试断言才能通过：那不是重构，是改行为，先跟用户确认。
- 改动范围超出最初圈定的文件。
- 冒出「顺手优化一下」的冲动：记下来单独排期。

## 平台限制

- `shell_exec` 每次 15s、无网络：重构后的验证要能在本地环境跑；跑不了就说明，并给出用户本地执行的命令。
- 空间文件区可用 `file_write` 直接改 ts / js / md / json / yaml；其它后缀走 `shell_exec`。
- 大范围重命名用 `shell_exec`（`grep -rl` + `sed`）比手改可靠，但改完要 `grep` 复查有没有漏。

## 报告

- 结构变化清单：每个变换一句话。
- 行为不变的证据：测试前后结果、对比输出。
- 有意保留的重复及原因（抽象错了比重复更贵）。
