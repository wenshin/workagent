# 代码审查

## 先定范围

- 只审用户给的改动（diff / 文件 / 目录），不顺手审全仓。
- 改动超过约 400 行时先按模块分批，一批一批给结论；一次给五十条意见没人看得完。

## 五个维度（按这个顺序看）

| 维度 | 看什么 | 典型问题 |
|---|---|---|
| 正确性 | 边界、空值、错误路径、并发、幂等 | 空列表崩溃；失败既不重试也不报错 |
| 安全 | 输入校验、鉴权、注入、密钥落盘、日志泄密 | 拼接 SQL；口令进日志 |
| 可维护性 | 命名、职责、重复、隐式约定 | 一个函数做四件事；魔法数字 |
| 可读性 | 是否 30 秒能读懂意图 | 变量叫 a / b；深层嵌套 |
| 性能 | 循环里查库、N+1、无上限增长 | 每次请求全表扫描 |

## 严重级别（每条结论都带级别）

- `blocker`：会出错、会丢数据、有安全风险 —— 必须改。
- `major`：现在能跑，但很快会咬人（并发、边界、错误处理缺失）—— 建议本次改。
- `minor`：可维护性问题 —— 可以下一轮。
- `nit`：风格偏好 —— 标明「可忽略」，不要为它争论。

## 写法

- 一条意见 = 位置（文件:行）+ 问题 + 为什么是问题 + 建议做法。不要只说「这里不太好」。
- 给出最小修改示例；多处同类问题时只示范一处，其余列位置。
- 明确说出「没发现问题」的部分，让用户知道哪些已经看过。
- **审查不改代码**：除非用户明确说「顺手修」，否则只出清单；改动另行确认。

## 不要做的

- 不要拿「不符合我的风格」当问题：没有团队规范时按可读性与内部一致性判断。
- 不要把猜测写成事实：不确定就问，或标注「需确认」。
- 不要复述 diff 内容当结论：用户已经知道改了什么，要的是判断。
- 不要因为行数多就只挑末尾几条：漏掉关键路径比挑刺更糟。
